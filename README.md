# Служба поддержки — ДЗ 1

Курсовая работа по дисциплине «Оптимизация клиент-серверных приложений», вариант 2. Автор: Дмитрий Кошеваров.

Пользователь создаёт заявку с категорией и ведёт переписку с поддержкой. Поддержка изменяет статусы, отвечает на заявки и видит сводку открытых обращений и нарушений норматива первой реакции. Администратор управляет пользователями, категориями и нормативами.

## Требования

- Python 3.12; Docker-образ и CI используют 3.12.12.
- PostgreSQL 17, запускается через Docker Compose v2.
- uv 0.9.8 и just.
- Node.js 22 или новее и npm — для тестов интерфейса.

Сервер: Litestar, Dishka, SQLAlchemy 2, asyncpg, Alembic. Интерфейс: HTML, CSS и JavaScript, отдельная сборка не требуется. Точные версии Python-зависимостей закреплены в `uv.lock`, зависимостей тестов интерфейса — в `package-lock.json`.

## Установка и локальный запуск

Получите исходники:

```sh
git clone https://github.com/krionefishy/Dmitrii_koshevarov_kursovay.git
cd Dmitrii_koshevarov_kursovay
```

Из корня проекта:

```sh
cp .env.example .env
uv sync --frozen
uv run --frozen python -c 'from pathlib import Path; import secrets; p=Path(".env"); p.write_text(p.read_text().replace("replace-with-a-random-secret-at-least-32-characters", secrets.token_urlsafe(48)))'
just infra-up
just db-migrate
just seed small
just serve
```

Интерфейс: http://127.0.0.1:8000. Интерактивное описание API: http://127.0.0.1:8000/api/docs. Проверка процесса: `/api/v1/health`, проверка подключения к БД: `/api/v1/ready`.

Если порт занят, измените `APP_PORT` или `DB_PORT` в `.env`. База по умолчанию — `dmitrii_koshevarov_helpdesk`, схема — `dmitrii_koshevarov`. Для остановки завершите сервер и выполните `just infra-down`; данные БД сохраняются в Docker volume.

## Программный интерфейс

База URL: `/api/v1`. JSON, UTF-8. OpenAPI: `/api/docs/openapi.json`. Успех POST — 201, кроме входа (200); GET/PATCH/PUT — 200. Ответы `Cache-Control: no-store`. DTO не раскрывают пароль, хеш и версию токена.

### Авторизация

`POST /auth/login`: `{"login":"customer","password":"Demo-password-2026!"}` → `access_token`, `token_type: bearer`, `expires_in`, `user`. Остальные операции требуют `Authorization: Bearer <token>`. JWT HS256 с обязательными sub/ver/iat/exp/iss/aud; роль берётся из БД на каждом запросе. `GET /auth/me` возвращает пользователя: login/display_name/role/is_active/created_at. Создание аккаунтов — только администратором; самостоятельной регистрации нет.

### Операции

| Метод / путь | Роль | Запрос и результат |
|---|---|---|
| POST `/auth/login` | Без токена | login, password → access_token, token_type, expires_in, user |
| GET `/auth/me` | Любая | UserDTO текущего пользователя |
| GET `/categories` | Любая | Page активных CategoryDTO; `include_inactive=true` включает отключённые для истории и фильтров |
| POST `/tickets` | customer | category_id, title (1–200), body (1–10000) → TicketDTO |
| GET `/tickets` | customer/support | Фильтры category_id, status; Page TicketDTO. Customer видит только свои |
| GET `/tickets/{id}` | Владелец/support | TicketDetail: TicketDTO + body, category, author_name, reaction |
| GET `/tickets/{id}/comments` | Владелец/support | Page CommentDTO, id ASC; `newest_first=true` — id DESC |
| POST `/tickets/{id}/comments` | Владелец/support | body (1–10000) → CommentDTO; признак ответа задаёт сервер |
| PATCH `/tickets/{id}/status` | support | status → TicketDTO |
| GET `/summary` | support/admin | as_of, open_count, breached_count, items всех категорий |
| GET `/admin/categories` | admin | Page всех категорий, включая отключённые |
| POST `/admin/categories` | admin | name (1–120), description (до 2000), response_seconds (1–2592000) → категория; норматив создаётся атомарно |
| PATCH `/admin/categories/{id}` | admin | name/description/is_active, хотя бы одно ненулевое поле |
| GET `/admin/norms` | admin | Page category_id/response_seconds |
| PUT `/admin/norms/{category_id}` | admin | response_seconds (1–2592000) → NormDTO |
| GET `/admin/users` | admin | Page UserDTO; курсор по login DESC |
| POST `/admin/users` | admin | login, display_name (1–120), role, password (10–128) → UserDTO |
| PATCH `/admin/users/{login}` | admin | display_name/role/is_active/password; хотя бы одно ненулевое поле |

Логин: `^[a-z][a-z0-9_]{2,63}$`. Роли: customer/support/admin. Пробелы в паролях сохраняются. Лишние поля тела запроса запрещены. Администратор не может отключить себя или снять с себя роль admin. Изменения пользователей сериализуются транзакционной advisory-блокировкой PostgreSQL; после ожидания роль и активность действующего администратора перечитываются, а при сокращении состава проверяется наличие активного admin. Изменение имени и повтор прежних role/is_active не отзывают JWT; фактическая смена роли/активности или задание пароля повышают auth_version.

Все входные ticket_id/category_id (path, query, body) находятся в диапазоне `1..9223372036854775807`; выход за диапазон даёт 400 до обращения к предметной таблице.

TicketDTO: id/author_login/category_id/title/status/response_norm_seconds/created_at/closed_at. CategoryDTO: id/name/description/is_active. CommentDTO: id/ticket_id/author_login/body/is_staff_reply/created_at. Все даты UTC ISO 8601; UI переводит в часовой пояс браузера.

### Бизнес-правила

Статусы: `new → in_progress → closed`; повторная установка того же статуса идемпотентна. Закрытую заявку нельзя комментировать или открыть повторно. Новая заявка возможна только в активной категории с положительным нормативом. Норматив копируется в заявку; последующие правки справочника его не меняют.

`reaction`: first_staff_reply_at (nullable), elapsed_seconds, norm_seconds, breached, as_of. Первый ответ — MIN даты комментария с is_staff_reply=true. Если ответа нет, срок считается от created_at до as_of для открытой заявки и до closed_at для закрытой; иначе до первого ответа. Закрытие не считается ответом поддержки. Превышение строго `>`, равенство допустимо. Переписка владельца и позднейшие ответы на первую реакцию не влияют. UI показывает часы, минуты и секунды, сохраняя дробные секунды с точностью timestamp (до микросекунд), чтобы округление не скрывало превышение.

Сводка включает только new/in_progress, по всем данным, включая категории без открытых заявок. Строка: category_id/category_name/open_count/breached_count/breached_share. Доля = breached_count/open_count, при нуле — 0. Категории, открытые заявки и первые ответы читаются одним SQL-оператором из согласованного снимка; итоговые показатели вычисляются в Python без кеша.

### Курсоры

Все списки: limit 1–100 (по умолчанию 20), cursor (opaque string). Ответ: `{"items": [...], "next_cursor": "..." или null, "has_more": true/false}`. Для следующей страницы передайте next_cursor без изменения фильтров/limit/пользователя. Total count не вычисляется. Пустая и последняя страницы: has_more=false, next_cursor=null.

Заявки/категории/нормативы упорядочены по числовому PK DESC, пользователи — login DESC, комментарии — id ASC по умолчанию или id DESC с `newest_first=true`. UI запрашивает последние 20, показывает их в хронологическом порядке и листает в историю кнопкой «Ранее»; после отправки открывает последние сообщения. Направление обхода и include_inactive входят в область курсора. Подписанный HMAC-SHA256 курсор содержит версию, последний ключ, верхнюю границу первой страницы и область запроса. Проверки роли и владельца повторяются независимо от курсора. OFFSET не используется.

Новые заявки/комментарии выше верхней границы не попадают в начатый обход. Это не транзакционный снимок между запросами: изменение фильтруемых полей может исключить строку или включить существующую строку. Для списка пользователей login не монотонный: новый логин ниже границы может появиться на последующих страницах. Обновление списка сбрасывает курсор.

### Ошибки

Тело содержит `detail`; для ошибок валидации Litestar может добавить `status_code`, `extra`.

| HTTP | Причина |
|---|---|
| 400 | Некорректное тело/параметр, лишнее поле, пустое изменение, повреждённый или несовместимый курсор |
| 401 | Нет токена, неверная подпись/срок, отключённый пользователь, отозванная версия токена |
| 403 | Роль не имеет прав на операцию |
| 404 | Нет ресурса, чужая заявка customer, отключённая категория при создании |
| 409 | Недопустимый переход, комментарий к закрытой заявке, занятый логин, отключение собственного admin или последнего активного admin |

### Наблюдаемость и служебные маршруты

Обычный запуск `just serve` / `just deploy-up` не подключает измерительные обработчики. Они включаются только отдельными точками входа `just serve-benchmark` / `just benchmark-up`. Клиент замеров запускается из `backend.benchmarks.runner`; при обращении к обычному серверу он завершится с указанием нужной команды запуска.

`X-Server-Ms` — время до начала отправки ответа, `X-DB-Ms` — сумма длительностей SQLAlchemy cursor execute, `X-SQL-Count` — количество этих SQL-вызовов. `Server-Timing` дублирует server/db. DB-время включает asyncpg/сеть; это не чистое CPU-время PostgreSQL. COMMIT, pool pre-ping, получение соединения и сериализация входят в серверное время, но не cursor-таймер. Клиентский RTT измеряется отдельно. Метрики живут в ContextVar запроса.

`GET /health` проверяет процесс; `GET /ready` выполняет SQL. Они, OpenAPI и статика не входят в таблицу бизнес-замеров.


## Организация бизнес-логики

HTTP-обработчики находятся в `routes.py` каждой области: `auth`, `categories`, `tickets`, `users`. Общий API-роутер только объединяет контроллеры; служебные проверки здоровья вынесены отдельно. Use case категорий и нормативов находятся в `categories/usecases.py`, пользователей — в `users/usecases.py`.

`TicketRules` содержит правила перехода статусов и расчёт первой реакции без обращения к БД. `auth_version` — версия авторизации пользователя: она входит в токен и увеличивается после смены пароля, роли или активности, чтобы прежний токен больше не принимался.

`shared/utils.py` объединяет `Clock`, `AppError` и `Paginator`. `Clock` даёт UTC-время и заменяется фиксированными часами в тестах. `AppError` передаёт ожидаемую прикладную ошибку в общий HTTP-обработчик. `Paginator` отвечает за страницы и проверку подписанных курсоров.
